# Q008 — Implement daemon single-instance lifecycle, local authentication and crash recovery

## Outcome

The `heniek` daemon enforces a single authenticated local instance, owns durable work independently of clients, and reconciles state after clean or unclean shutdown.

## Specification anchors

- §6.1 Local daemon
- §6.3 Local transports and authentication
- §18 Durability and recovery

## Dependency

Requires Q007 to be merged and independently confirmed on remote `main`.

## Tier

`T1-foundation`

## Constraints

- Use restrictive runtime-file permissions and rotating local credentials.
- Never infer provider-process survival without reconciliation.
- Preserve Product Specification v0.2 commitments and acceptance criteria.
- Keep Windmill, predecessor automation tooling, and TAKT out of Heniek runtime dependencies.
- Use strict ESM TypeScript, provider-neutral public contracts, and repository conventions.

## Exclusions

- No remote daemon access.
- No promise to resurrect every provider process after reboot.
- No factory runtime state, credentials, transcripts, or control artifacts in this repository.
- No unrelated backlog work or speculative scope reduction.

## Acceptance criteria

- [ ] Concurrent starts converge on one healthy instance and stale PID/socket files recover safely.
- [ ] Unauthenticated or replayed clients cannot call daemon methods.
- [ ] Restart classification distinguishes resumable, failed, cancelled, and unknown external work.
- [ ] Public contracts and generated schemas remain compatible or are versioned deliberately.
- [ ] `pnpm check` passes from a clean checkout on Node.js 24.
- [ ] The pull request is non-draft, self-contained, and uses `Closes <this issue>`.

## Required tests

- Parallel-start, stale-file, auth replay, SIGTERM, and SIGKILL tests.
- Recovery tests against deterministic backend handles.
- Regression tests for every defect discovered while implementing this issue.

## Required evidence

- Lifecycle state-transition trace.
- Permission and authentication test report.
- Exact commands and results for local checks.
- GitHub required-check and merge confirmation.

markers disagree, a product commitment would need to be narrowed, a required
subscription route cannot be proven, credentials could be exposed, or a genuine
technical ambiguity remains after the issue's bounded spike/ADR path.
