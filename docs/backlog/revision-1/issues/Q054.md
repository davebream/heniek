# Q054 — Implement durable inbox, product notifications and macOS notifications

## Outcome

A durable notification projection drives in-product inbox events and privacy-preserving macOS notifications with deduplication and acknowledgement.

## Specification anchors

- §17.4 Durable inbox and notifications
- §25 Notifications and inbox
- §27.1 Confidential-code default

## Dependency

Requires Q053 to be merged and independently confirmed on remote `main`.

## Tier

`T2-capability`

## Constraints

- Notification payloads omit confidential task content by default.
- Persist before delivery and record delivery/ack state.
- Preserve Product Specification v0.2 commitments and acceptance criteria.
- Keep Windmill, Kombajn, and TAKT out of Heniek runtime dependencies.
- Use strict ESM TypeScript, provider-neutral public contracts, and repository conventions.

## Exclusions

- No cloud push service.
- No notification as canonical interaction state.
- No factory runtime state, credentials, transcripts, or control artifacts in this repository.
- No unrelated backlog work or speculative scope reduction.

## Acceptance criteria

- [ ] Questions, approvals, failures, recoveries, and completion create deduplicated events.
- [ ] macOS permission denial or helper failure does not block runs.
- [ ] Read/ack/dismiss state remains consistent across CLI, TUI, web, and restart.
- [ ] Public contracts and generated schemas remain compatible or are versioned deliberately.
- [ ] `pnpm check` passes from a clean checkout on Node.js 24.
- [ ] The pull request is non-draft, self-contained, and uses `Closes <this issue>`.

## Required tests

- Notification projection/idempotency property tests.
- macOS adapter permission, failure, privacy, and restart tests.
- Regression tests for every defect discovered while implementing this issue.

## Required evidence

- Notification event matrix.
- Redacted macOS delivery and fallback report.
- Exact commands and results for local checks.
- GitHub required-check and merge confirmation.
