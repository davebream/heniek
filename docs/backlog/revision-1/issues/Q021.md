# Q021 — Implement account queues, concurrency, fallback chains and permissions

## Outcome

Per-account queues, concurrency leases, explicit fallback chains, and broad-but-bounded workspace permissions schedule work without credential races or silent provider substitution.

## Specification anchors

- §9.6 Concurrency and queues
- §9.7 Execution permissions
- §24 Limits, retries, and safeguards

## Dependency

Requires Q020 to be merged and independently confirmed on remote `main`.

## Tier

`T2-capability`

## Constraints

- Fallback order is configuration, not model choice.
- The strictest applicable limit wins.
- Preserve Product Specification v0.2 commitments and acceptance criteria.
- Keep Windmill, Kombajn, and TAKT out of Heniek runtime dependencies.
- Use strict ESM TypeScript, provider-neutral public contracts, and repository conventions.

## Exclusions

- No automatic quota-based account rotation.
- No fine-grained per-tool permission DSL.
- No factory runtime state, credentials, transcripts, or control artifacts in this repository.
- No unrelated backlog work or speculative scope reduction.

## Acceptance criteria

- [ ] Account concurrency is enforced across runs and survives restart.
- [ ] Fallback occurs only for classified eligible failures and records why each candidate was selected or rejected.
- [ ] Execution permissions cannot escape the assigned workspace or secret allowlist.
- [ ] Public contracts and generated schemas remain compatible or are versioned deliberately.
- [ ] `pnpm check` passes from a clean checkout on Node.js 24.
- [ ] The pull request is non-draft, self-contained, and uses `Closes <this issue>`.

## Required tests

- Fairness, starvation, lease expiry, and fallback classification tests.
- Workspace escape and disallowed-secret integration tests.
- Regression tests for every defect discovered while implementing this issue.

## Required evidence

- Queue/fallback decision trace.
- Isolation test report.
- Exact commands and results for local checks.
- GitHub required-check and merge confirmation.

## Autonomous stop conditions

Stop with a typed blocker and evidence if the predecessor is not merged, queue
markers disagree, a product commitment would need to be narrowed, a required
subscription route cannot be proven, credentials could be exposed, or a genuine
technical ambiguity remains after the issue's bounded spike/ADR path.
