## Context

The V4 execution boundary could identify the selected profile and return a small usage summary, but
it could not say whether a number was exact, estimated, absent, malformed, contradictory, or unsafe.
It also had no provider-neutral context-pressure signal. That made cross-engine comparison lossy and
made smart continuation (§15.3) impossible to implement conservatively.

The boundary must remain additive. Existing V1–V4 schemas are compatibility artifacts, and provider
payload names belong in execution adapters rather than public contracts. Q019 therefore adds a V5
backend boundary and a separate V1 telemetry snapshot without changing any legacy schema.

## Decisions

### D1 — every metric carries availability and confidence

`ExecutionTelemetryV1` wraps every numeric metric in one of these two forms:

```text
available(value, exact | estimated) | unavailable(reason)
```

Unavailable reasons are `not_reported`, `unsupported`, `invalid`, `contradictory`, `overflow`, and
`counter_reset`. The snapshot always identifies `engine`, `executionMode`, opaque local
`evidenceRefs`, and provider-session availability. It groups input, output, combined cached input,
cache-read, cache-write, total usage, cost, wall/API duration, context used/window, utilization, and
pressure. Public names use `Units`; provider token-shaped fields remain confined to adapters and
sanitized fixtures.

`ExecutionResultV4`, `ExecutionEventV3`, and `ExecutionBackendV5` are additive. V1–V4 remain exported
and their generated bytes and hashes are unchanged.

### D2 — a focused reducer owns provider-neutral aggregation

The reducer accepts normalized observations classified as `delta`, `cumulative`, or `gauge`.

- Delta counters add only while arithmetic remains finite and safe.
- A cumulative decrease begins a new epoch: the new counter is added without a negative delta and
  the aggregate becomes estimated.
- Unsafe integers and arithmetic overflow become unavailable with `overflow`.
- Invalid numeric input becomes unavailable with `invalid`; missing input remains `not_reported`.
- Conflicting provider-session identities become unavailable with `contradictory`.

The reducer has no provider DTO vocabulary. Claudexor field extraction and the distinction between
Claude's combined cached-input counter and the other engines' cache-read counter stay in
`@heniek/execution-claudexor`.

### D3 — context pressure is independent from billing usage

Pressure has three states: measured utilization, typed capacity exhaustion, or unavailable.

```text
capacity signal → exhausted
otherwise max(valid reported ratio, valid used/window ratio) → measured
otherwise → unavailable
```

A capacity-exhaustion signal always wins. When reported utilization and a used/window ratio disagree,
the reducer selects the higher valid ratio and downgrades confidence to estimated. Equal signals keep
the reported confidence. Cumulative input/output billing counters are never treated as live context
occupancy. Native Claude's documented status-line totals changed meaning in 2.1.132: they now
describe the current window, while `current_usage` provides the component split. The mapping uses
current input/window and the rounded `used_percentage`; immediately after compaction,
`current_usage` may be null, so component metrics remain unavailable until the next API response.

### D4 — coverage reflects what each pinned route actually reports

| Route | Session | Usage/cache | Cost | Duration | Context pressure |
| --- | --- | --- | --- | --- | --- |
| External Claude 2.1.165 recorded result | exact | input/output and raw cache read/write exact | client estimate | wall/API exact | unavailable on this result route |
| Codex CLI 0.146.0 recorded JSONL | exact | input/output/cache-read exact | not reported | not reported | unavailable on the pinned CLI route |
| Cursor pinned Q018 observation | exact | input/output/cache-read exact | not reported | not reported | unsupported |
| Native Claude documented status line (2.1.132+) | exact | current input/output/cache split exact | client estimate | wall/API exact | current input/window plus reported percentage; conservative maximum estimated |

The external Claude fixture preserves the raw split cache fields. Claudexor V2 currently collapses
those fields into `cachedInputTokens`; the live V5 adapter therefore reports `cachedInputUnits` and
leaves cache-read/cache-write unavailable instead of inventing a split. Codex and Cursor's normalized
cached-input field is pinned to cache-read by their recorded evidence.

Native Claude is a documentation-backed mapping fixture, not evidence that Heniek executes the
native bridge. Q023 still owns that bridge. The fixture labels this provenance explicitly and pins
the post-2.1.132 semantics rather than applying them retroactively to older versions.

### D5 — evidence is useful without carrying sensitive provider data

The fixture matrix records source versions, raw field paths, sanitized values, expected normalized
snapshots, and non-sensitive evidence references. It contains no raw DTO object, transcript,
credential, control URL, or real session identifier. Runtime snapshots may expose an opaque local
provider-session identity to their caller, but provider payload keys never cross the adapter boundary.

## Consequences and boundaries

- Smart continuation can consume a conservative live pressure union without depending on any
  engine's payload shape.
- Exact and estimated counters remain comparable without pretending unavailable fields are zero.
- The V5 Claudexor profile adapters cover Claude, Codex, and Cursor. Native Claude mapping is fixture
  coverage only until Q023 supplies the execution bridge.
- No database migration, persistence, upload, cloud analytics, telemetry UI, or durable stage-level
  aggregation is introduced. Stage-runtime work owns durable aggregation later.
- Evidence references are opaque local pointers, not a promise that raw provider artifacts are
  checked into a registered repository.
- A future adapter can add observations without changing the reducer or the public schema, provided
  it preserves aggregation semantics and truthful availability.
